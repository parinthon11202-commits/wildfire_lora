# คำอธิบายฟังก์ชันโหนด FG1 ก่อนคอมไพล์เป็น `.bin`

เอกสารนี้อธิบายซอร์สโค้ด **โหนดระบบ FG1 ปัจจุบัน** ตาม 6 ไฟล์ในภาพที่ผู้ใช้ส่งมา เพื่อให้อ่านโค้ดและอธิบายต่ออาจารย์ได้ตรงกับการทำงานจริง ข้อความนี้อธิบายโค้ดในโปรเจกต์ ไม่ใช่ผลทดสอบบอร์ดจริง และยังไม่ได้ยืนยันว่าไฟล์ `.bin` ที่ VM เผยแพร่อยู่ตรงกับซอร์สชุดนี้ทุกบรรทัด

## เริ่มอ่านจากตรงไหน

ไฟล์เริ่มต้นคือ [`provisioned_sensor.ino`](../provisioned_sensor/provisioned_sensor.ino) ซึ่งเรียก `setupNode()` ตอนเปิดเครื่อง และ `runOneMeasurementCycle()` ใน `loop()` โค้ดส่วนใหญ่ถูกแยกไปอยู่ในไฟล์ `.h` แล้วนำเข้าด้วย `#include` เมื่อคอมไพล์ ดังนั้นไฟล์ `.ino` สั้นไม่ได้หมายความว่าโปรแกรมมีงานน้อย

```text
เปิดเครื่อง / ตื่นจาก deep sleep
  → setupNode() → โหลดตัวตนโหนด → เตรียมเซนเซอร์และ LoRa
  → runOneMeasurementCycle()
  → readSensors() → evaluateFireStatus()
  → sendMeasurement() → ส่ง LoRa → รอ ACK/คำสั่งจาก Gateway
  → รอรอบถัดไปหรือเข้า deep sleep
```

`NODE03` ไม่มีซอร์สหรือ `.bin` แยก โหนด NODE01–NODE10 ใช้โปรแกรมกลางชุดเดียวกัน แล้วกำหนดหมายเลขและกุญแจเฉพาะบอร์ด **หลังแฟลช** ผ่าน USB

## คำศัพท์ที่ใช้ในโค้ด

| คำ | ความหมายในระบบนี้ |
|---|---|
| `NVS` / `Preferences` | พื้นที่เก็บข้อมูลถาวรในแฟลช ESP32; ยังอยู่หลังปิดไฟหรือรีเซ็ต |
| `RTC_DATA_ATTR` | ตัวแปรที่คงค่าได้ระหว่าง deep sleep; ไม่ใช้แทน NVS สำหรับข้อมูลที่ต้องอยู่หลังไฟดับ |
| `slot` | เลขประจำโหนด 1–10; เช่น slot 3 แสดงเป็น `NODE03` |
| `generation` | รุ่นของกุญแจโหนด ใช้แยกการลงทะเบียนครั้งใหม่ออกจากครั้งเก่า |
| `sequence` | เลขลำดับการส่งที่ห้ามใช้ซ้ำกับกุญแจเดิม |
| `ACK` | ข้อความตอบจาก Gateway ว่ารับข้อมูลหรือมีคำสั่งส่งกลับ |
| `frame` | ข้อมูลหนึ่งชุดที่ส่งทางวิทยุ LoRa; มีส่วนหัว ข้อมูลที่เข้ารหัส และรหัสตรวจสอบ |

## 1. [`provisioned_sensor/secure_node.h`](../provisioned_sensor/secure_node.h): ตัวตน การลงทะเบียน และ LoRa ที่เข้ารหัส

ไฟล์นี้เป็นส่วนที่ผู้ใช้เคยวางมา `FgNodeIdentity` เป็น **โครงสร้างข้อมูล ไม่ใช่ฟังก์ชัน** ประกอบด้วย `magic` สำหรับตรวจรูปแบบข้อมูล, `slot`, `generation` 8 ไบต์, `key` 32 ไบต์ และ `reservedSequence` สำหรับจำเลขลำดับที่จองไว้แล้ว กุญแจเฉพาะ NODE03 ไม่ได้เขียนค้างในซอร์สโค้ดกลางนี้

| ฟังก์ชัน | คำอธิบายภาษาไทย |
|---|---|
| `storeSecureIdentity(identity)` | เปิดพื้นที่ NVS ชื่อ `fg_identity` แล้วบันทึกโครงสร้างตัวตนทั้งชุดเป็นข้อมูลไบนารี หากบันทึกครบจึงคืน `true` ถ้าบันทึกไม่ได้คืน `false` |
| `loadSecureIdentity()` | อ่านตัวตนจาก NVS ตรวจขนาดข้อมูล `magic`, slot 1–10 และช่วงของเลขลำดับ ถ้าถูกต้องจะสร้างชื่อ `NODE01`–`NODE10` จาก slot และคืน `true` |
| `setupSecureNode()` | จัดการช่วงตั้งค่าทาง USB หลังเริ่มเครื่อง ถ้ายังไม่ลงทะเบียนจะรออยู่ในโหมดตั้งค่าและประกาศ `FG1_READY` ซ้ำ; ถ้าลงทะเบียนแล้วและเป็นการรีเซ็ตปกติ จะเปิดช่วงรับคำสั่งประมาณ 10 วินาที; ถ้าตื่นจาก timer ของ deep sleep จะข้ามช่วงนี้ เมื่อได้รับ `FG_SETUP` จะรอตั้งค่า, ตรวจข้อความ `fg_provision`, บันทึก slot/generation/key แล้วตอบ `fg_provisioned` พร้อมหลักฐาน HMAC ให้ Server ตรวจ `fg_start` จึงให้ออกจากโหมดตั้งค่า |
| `nextSecureSequence(sequence)` | จ่ายเลขลำดับใหม่สำหรับการส่งหนึ่งครั้ง หากไม่มีช่วงเลขที่ใช้ได้ จะจองล่วงหน้า 256 หมายเลขและ **บันทึกขอบเขตลง NVS ก่อนส่ง** จากนั้นใช้ตัวนับใน RTC ระหว่าง deep sleep วิธีนี้ช่วยไม่ให้ใช้เลขเดิมซ้ำหลังไฟดับ; ถ้า NVS บันทึกไม่ได้จะไม่อนุญาตให้ส่ง |
| `prepareSecurePayload(payload, payloadLength, frame)` | ขอเลขลำดับจากฟังก์ชันก่อนหน้า แล้วสร้างเฟรมขาออก `FGU1` ที่มี slot/generation/sequence และเข้ารหัส payload ด้วยกุญแจของโหนด คืนความยาวเฟรม หรือ `0` ถ้าทำไม่ได้ |
| `transmitPreparedSecureFrame(frame, length)` | ตรวจรูปแบบเฟรม `FGU1` ที่เตรียมไว้ แล้วส่งไบต์เดิมผ่าน LoRa โดยตรง ใช้ตอนลองส่งซ้ำเพื่อไม่สร้าง ciphertext หรือ sequence ใหม่ |
| `transmitSecurePayload(payload)` | รับข้อความ `String` สร้างเฟรมเข้ารหัส แล้วเรียกฟังก์ชันส่งเฟรม ใช้กับข้อมูลชนิดข้อความ เช่น GPS หรือผลคำสั่ง |
| `receiveSecureReply(payload)` | อ่านเฟรมตอบจาก Gateway ถอดรหัสด้วยกุญแจของโหนด ตรวจว่าเป็นขากลับ `FGD1`, slot/generation ตรง และ sequence ตรงกับครั้งที่เพิ่งส่ง ถ้าเป็น reply แบบย่อจะแปลงเป็นข้อความที่ส่วนจัดการ ACK/คำสั่งอ่านต่อได้; ถ้าตรวจไม่ผ่านคืน `false` |

**เหตุผลของ `sequence`:** โค้ดเข้ารหัส FG1 ใช้ AES-256-GCM โดยสร้าง nonce จากทิศทางและเลขลำดับ การส่งซ้ำจึงต้องส่งเฟรมเดิมทั้งชุด และการส่งครั้งใหม่ต้องใช้เลขใหม่ ดูรูปแบบเฟรมใน [`radio_common/secure_frame.h`](../radio_common/secure_frame.h)

**ลำดับลงทะเบียน NODE03:** เว็บแฟลชเฟิร์มแวร์ → เปิด USB อีกครั้ง → ส่ง `FG_SETUP` → โหนดตอบ `FG1_READY` → เว็บขอข้อมูลลงทะเบียน NODE03 จาก Server → ส่ง `fg_provision` ผ่าน USB → โหนดบันทึกและส่ง proof → Server ตรวจ proof และเปลี่ยนสถานะเป็น active → เว็บส่ง `fg_start` ดูฝั่งเว็บที่ [`serialNodeSetup.ts`](../wildfire-dashboard/src/admin/serialNodeSetup.ts)

## 2. [`provisioned_sensor/config.h`](../provisioned_sensor/config.h): ค่ากำหนดก่อนคอมไพล์

ไฟล์นี้ **ไม่มีฟังก์ชัน** แต่กำหนดวิธีที่คอมไพเลอร์จะประกอบโปรแกรม:

| คำสั่ง | ความหมาย |
|---|---|
| `#pragma once` | ป้องกันการนำไฟล์ header นี้เข้าซ้ำในรอบคอมไพล์เดียวกัน |
| `#define SECURE_LORA_ENABLED 1` | เปิดเส้นทางส่งข้อมูล FG1 ที่เข้ารหัส; โค้ดภายใต้ `#if SECURE_LORA_ENABLED` จึงถูกนำมาคอมไพล์ |
| `#define NODE_ID secureNodeId` | ใช้ชื่อโหนดที่โหลดจาก NVS หลังลงทะเบียน แทนการพิมพ์ `NODE03` ลงในซอร์ส |
| `#include "../sensor_common/sensor_config.h"` | นำค่าขาอุปกรณ์, LoRa 433 MHz, GPS และเวลาต่าง ๆ จากไฟล์ส่วนกลางมาใช้ |

ตัวอย่างค่าจาก [`sensor_config.h`](../sensor_common/sensor_config.h): LoRa 433 MHz, SF10, bandwidth 125 kHz, SHT31 ที่ I²C และ Sharp ที่ขา ADC ค่าฝั่งโหนดและ Gateway ที่เกี่ยวกับวิทยุต้องสอดคล้องกัน

## 3. [`sensor_common/node_app.h`](../sensor_common/node_app.h): ลำดับงานหลัก

| ฟังก์ชัน | คำอธิบายภาษาไทย |
|---|---|
| `setupNode()` | เริ่ม Serial, โหลด/ตั้งค่าตัวตน FG1, เตรียมตัวแปรและคำสั่งที่เคยทำ, เริ่มเซนเซอร์กับวิทยุ LoRa และเริ่มงาน GPS เมื่อเปิดใช้ เป็นฟังก์ชันที่ `setup()` ใน `.ino` เรียก |
| `runOneMeasurementCycle()` | ทำงานหนึ่งรอบ: อ่านเซนเซอร์ → ประเมินสถานะ → กำหนดเวลารอบ → ส่งข้อมูลทันที → จัดการ GPS → รอหรือหลับจนถึงรอบถัดไป `WARNING` ทำงานต่อเนื่อง; สถานะอื่นอาจเข้า deep sleep เมื่อไม่มีงาน GPS ค้าง |
| `sendMeasurement(current, status)` | เลือกวิธีส่งค่าที่วัดได้ สำหรับ FG1 ปัจจุบัน (`SECURE_LORA_ENABLED=1`) จะเรียก `sendCompactMeasurement()` เพื่อส่งข้อมูลแบบย่อที่เข้ารหัส; แขนง JSON ดิบเป็นทางเลือกของโค้ด legacy เมื่อปิด FG1 |

## 4. [`sensor_common/sensor_reading.h`](../sensor_common/sensor_reading.h): อ่านอุปกรณ์ตรวจวัด

| ฟังก์ชัน | คำอธิบายภาษาไทย |
|---|---|
| `powerSensors(on)` | เปิดหรือปิดไฟเลี้ยงเซนเซอร์ผ่านขาที่กำหนด ถ้าขานั้นเป็น `-1` จะไม่สั่งสวิตช์; จำสถานะล่าสุดเพื่อลดการสั่งซ้ำ และรอให้ไฟนิ่งหลังเปิด |
| `median3(a, b, c)` | คืนค่ากลางของตัวเลขสามค่า เพื่อลดผลจากค่าที่กระโดดผิดปกติหนึ่งครั้ง |
| `readSharpOnce()` | เปิด LED ของ Sharp GP2Y1014 ชั่วครู่ อ่านค่า ADC ตามจังหวะที่ตั้งไว้ แล้วปิด LED คืนค่า ADC ดิบ |
| `readParticleMedianAdc()` | เรียก `readSharpOnce()` สามครั้ง เว้นช่วงสั้น ๆ แล้วใช้ `median3()` เลือกค่ากลาง |
| `beginSht31()` | ลองเริ่มเซนเซอร์ SHT31 ที่ I²C address `0x44` หากไม่สำเร็จจึงลอง `0x45` คืนผลว่าสื่อสารได้หรือไม่ |
| `initSensors()` | ตั้งขา I²C, ขาควบคุมไฟ, ขา LED ของ Sharp, ADC 12 บิต แล้วเริ่ม SHT31 พร้อมแสดงผลทาง Serial |
| `readSensors()` | เปิดไฟเซนเซอร์เมื่อจำเป็น อ่านอุณหภูมิและความชื้นจาก SHT31 และอ่านค่ากลาง ADC จาก Sharp คืนค่ารวมเป็น `SensorData` |

**ข้อควรพูดให้ถูก:** `particleAdc` เป็นค่า ADC ดิบช่วง 0–4095 ที่ใช้เป็นตัวบ่งชี้ตามเกณฑ์ในโค้ด ไม่ใช่ค่าความเข้มข้น PM2.5 หน่วย µg/m³ ที่ผ่านการสอบเทียบแล้ว

## 5. [`sensor_common/risk_rules.h`](../sensor_common/risk_rules.h): ตัดสินระดับความเสี่ยง

| ฟังก์ชัน | คำอธิบายภาษาไทย |
|---|---|
| `evaluateRawRisk(data)` | ตรวจค่าผิดปกติของเซนเซอร์ก่อน แล้วเทียบอุณหภูมิ ความชื้น และ ADC กับเกณฑ์ คืนสถานะเบื้องต้น `SENSOR_FAULT`, `WARNING`, `WATCH` หรือ `NORMAL` |
| `applyStateLatch(raw)` | ทำให้สถานะไม่แกว่งเมื่อค่าขึ้นลงใกล้เกณฑ์: เพิ่มระดับทันที แต่จะลดระดับหลังอ่านค่าต่ำลงต่อเนื่อง 3 รอบ; `SENSOR_FAULT` เข้าทันทีและเมื่อเซนเซอร์กลับมาปกติจะกลับไปตามผลวัดใหม่ |
| `evaluateFireStatus(data)` | จุดเรียกใช้งานจริง รวม `evaluateRawRisk()` กับ `applyStateLatch()` แล้วคืนสถานะสุดท้ายที่จะส่ง |
| `plannedReportIntervalSeconds(status)` | คืนเวลารอบวัด/ส่ง: `WATCH` 40 วินาที, `WARNING` 20 วินาที, `NORMAL` และ `SENSOR_FAULT` 60 วินาที |

เกณฑ์ในซอร์ส ณ เวลาจัดทำเอกสาร:

| สถานะ | เงื่อนไขเด่น |
|---|---|
| `SENSOR_FAULT` | อุณหภูมิ/ความชื้นเป็น NaN หรืออยู่นอกช่วงที่รับได้ หรือ ADC นอก 0–4095 |
| `WARNING` | อุณหภูมิ >45°C **หรือ** ADC >1100 **หรือ** อุณหภูมิ ≥30°C พร้อมความชื้น ≤30% |
| `WATCH` | อุณหภูมิ >35°C **หรือ** ADC >300 **หรือ** ความชื้น <50% |
| `NORMAL` | ไม่เข้าเงื่อนไขข้างต้น |

การตรวจเรียงตามลำดับในโค้ด: `SENSOR_FAULT` → `WARNING` → `WATCH` → `NORMAL` ดังนั้นถ้าหลายเงื่อนไขเกิดพร้อมกันจะเลือกสถานะที่ตรวจพบก่อน แล้วจึงผ่านตัวหน่วงการลดระดับ

## 6. [`sensor_common/lora_transport.h`](../sensor_common/lora_transport.h): ส่งข้อมูลไป Gateway

| ฟังก์ชัน | คำอธิบายภาษาไทย |
|---|---|
| `initLoRa()` | ตั้งขา SPI และเริ่มชิป LoRa ด้วยความถี่/SF/bandwidth/coding rate/sync word จาก config หากเริ่มไม่ได้จะบันทึกเวลาไว้และคืน `false` |
| `ensureLoRaReady()` | ตรวจว่าวิทยุพร้อมหรือไม่ ถ้ายังไม่พร้อมจะลองเริ่มใหม่เมื่อผ่านเวลารอที่กำหนด ไม่เริ่มซ้ำถี่ทุกครั้ง |
| `buildJsonPacket(data, status)` | สร้าง JSON ย่อที่มีรหัสโหนด เวลารอบ สถานะ อุณหภูมิ ความชื้น และ ADC ใช้ในแขนงส่งเซนเซอร์แบบ legacy; **FG1 ปัจจุบันใช้ compact binary สำหรับค่าตรวจวัด** |
| `listenForGatewayCommand(waitForSensorAck)` | ในไฟล์นี้มีเพียง **การประกาศชื่อฟังก์ชันล่วงหน้า** ตัวฟังก์ชันจริงอยู่ใน [`gateway_commands.h`](../sensor_common/gateway_commands.h) ทำหน้าที่รอ ACK หรือคำสั่งจาก Gateway ภายในช่วงรับสูงสุด 6 วินาที |
| `remainingRadioCycleMs()` | คำนวณเวลาเหลือในรอบวัด/ส่ง เพื่อไม่เริ่มการสื่อสารใหม่เมื่อเวลาไม่พอ |
| `radioExchangeCostMs(frameLength, receiveReply)` | ประมาณเวลาที่ต้องใช้ส่งเฟรม ประมวลผล และหากต้องรอคำตอบก็เผื่อช่วงรับกับเวลาส่งผลคำสั่ง |
| `waitForRadioTurn(frameLength, maximumDelayMs, receiveReply)` | ตรวจว่ายังมีเวลาพอสำหรับการสื่อสารครบชุด แล้วสุ่มหน่วงก่อนส่งเพื่อลดโอกาสชนกับโหนดอื่น; ถ้าเวลาไม่พอจะเลื่อนการส่ง |
| `sendCompactMeasurement(data, status)` | ทางส่งค่าตรวจวัดหลักของ FG1: แปลงข้อมูลเป็น compact binary, เตรียมเฟรมเข้ารหัส, ส่ง LoRa และรอ ACK ถ้าไม่ได้ ACK จะลองซ้ำได้ไม่เกิน 3 ครั้ง โดยใช้ **เฟรมและ sequence เดิม** |
| `sendLoRaPacket(payload, useRandomDelay, requireGatewayAck)` | ทางส่งข้อความทั่วไป เช่น GPS หรือผลคำสั่ง ตรวจวิทยุ/เวลา สุ่มหน่วงตามที่สั่ง แล้วส่งแบบเข้ารหัสในโหมด FG1 จากนั้นเปิดรับ ACK/คำสั่ง; คืนผลว่าการส่งสำเร็จตามเงื่อนไขที่ขอหรือไม่ |

## แยกเรื่องคอมไพล์ การแฟลช และการลงทะเบียน

1. **คอมไพล์:** Arduino CLI รวม `.ino`, `.h`, ไลบรารี และ ESP32 core ให้เป็นโปรแกรมเครื่อง โหนดใช้บอร์ดเป้าหมาย `esp32:esp32:ttgo-lora32:FlashFreq=40`
2. **เผยแพร่ไฟล์:** [`publish-node-firmware.ps1`](../scripts/publish-node-firmware.ps1) นำผลคอมไพล์มาจัดเป็น `node-app.bin` พร้อม bootloader, partition และ boot app แล้วสร้าง `manifest.json` กับค่าแฮช สคริปต์นี้ไม่ได้คอมไพล์หรือแฟลชบอร์ด
3. **แฟลช:** หน้าเว็บดาวน์โหลดและตรวจไฟล์ `.bin` ก่อนใช้ Web Serial เขียนลง ESP32
4. **ลงทะเบียน:** หลังแฟลช เว็บเปิดพอร์ตอีกครั้งเพื่อส่งรหัส NODE03 และกุญแจผ่าน USB ขั้นตอนนี้ไม่สร้าง `.bin` ใหม่

Gateway เป็นอีกสเก็ตช์หนึ่ง เริ่มที่ [`gateway/gateway.ino`](../gateway/gateway.ino) และคอมไพล์แยกจากโหนด การกดติดตั้ง NODE03 บนหน้าเว็บไม่ได้แฟลช Gateway

## คำอธิบายสั้นสำหรับพูดกับอาจารย์

> โค้ดต้นฉบับของโหนดเริ่มที่ `provisioned_sensor.ino` แล้วเรียกฟังก์ชันในไฟล์ `.h` ที่แยกตามหน้าที่: ตั้งค่าตัวตน อ่านเซนเซอร์ ประเมินสถานะ และส่งข้อมูล LoRa อย่างเข้ารหัส เมื่อนำโค้ดทั้งหมดไปคอมไพล์จะได้ `.bin` กลางสำหรับโหนดทุกตัว หลังติดตั้งจึงใช้ USB ลงทะเบียนให้บอร์ดเป็น NODE03 และให้กุญแจเฉพาะตัว Gateway ใช้โค้ดและเฟิร์มแวร์อีกชุดหนึ่งเพื่อรับ LoRa แล้วส่งต่อ Server
