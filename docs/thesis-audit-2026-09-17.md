## ผลสำคัญ

**เล่มยังไม่สอดคล้องกับโค้ดปัจจุบัน แม้รูป 3.6–3.7 จะปรับบางส่วนแล้ว** ข้อความ ตารางทดสอบ และภาพฐานข้อมูลหลายแห่งยังเป็นระบบ Baseline และคะแนนความเสี่ยงรุ่นเก่า ขณะที่ซอร์สปัจจุบันใช้ `risk_model_version = 7` และเกณฑ์คงที่พร้อมการคงสถานะก่อนลดระดับ

ต้องปรับอย่างน้อย 6 เรื่องร่วมกันทั้งเล่ม:

1. เกณฑ์ประเมินและกลไกเปลี่ยนสถานะ: ไม่มี CALIBRATING, CRITICAL, Baseline, EMA, Rate of Change หรือคะแนนความเสี่ยงในเส้นทางประเมินปัจจุบัน
2. หน่วยอนุภาค: ใช้ `pm`/`particle_ug_m3` เป็นค่าประมาณจาก Sharp ไม่ใช่ ADC raw และยังไม่ใช่ PM2.5 ที่สอบเทียบกับเครื่องอ้างอิง
3. บทบาท Backend: ตรวจแพ็กเก็ตและใช้สถานะจากโหนด ไม่คำนวณเกณฑ์หรือคะแนนซ้ำ
4. คำสั่งควบคุม: รองรับ GPS สองคำสั่ง ไม่มี baseline_recalibrate ในระบบปัจจุบัน
5. แผนทดสอบต้องใช้เกณฑ์รุ่น 7 และแยกจากผลทดลองรุ่นเก่า
6. ภาพผัง/ภาพหน้าจอต้องแสดงขั้นตอนและข้อมูลรุ่นเดียวกับข้อความ

### 1.2 เกณฑ์ประเมินดิบ ก่อนผ่านการคงสถานะ

ให้ T เป็นอุณหภูมิ (°C), RH เป็นความชื้นสัมพัทธ์ (%RH), P เป็นความเข้มข้นอนุภาคโดยประมาณจาก Sharp (µg/m³)

| ลำดับ | เงื่อนไข | ผลดิบ |
|---|---|---|
| 1 | ตรวจพบความผิดปกติของข้อมูล SHT31 หรือ Sharp ตามฟังก์ชันตรวจสอบ | SENSOR_FAULT |
| 2 | T > 45 หรือ P > 150 หรือ (T ≥ 30 และ RH ≤ 30) | WARNING |
| 3 | ยังไม่เข้า WARNING และ (T > 35 หรือ P > 50 หรือ RH < 50) | WATCH |
| 4 | ไม่เข้าเงื่อนไขข้างต้น | NORMAL |

เงื่อนไขใช้ **หรือ** ดังนั้น T หรือ P เพียงค่าเดียวก็ทำให้เกิด WARNING ได้ ไม่ถูกต้องที่จะเขียนว่าต้องมีควันร่วมกับความร้อนเสมอ หรือว่าระบบรอยืนยัน 2 รอบก่อนยกระดับ

หลังประเมินดิบ ระบบยกระดับทันที แต่ลด WARNING เป็น WATCH เมื่อผลดิบต่ำกว่า WARNING ต่อเนื่อง 3 รอบ และลด WATCH เป็น NORMAL เมื่อผลดิบเป็น NORMAL ต่อเนื่อง 3 รอบ ถ้ากลับถึงระดับที่คงอยู่ ตัวนับการลดระดับจะเริ่มใหม่ กรณี SENSOR_FAULT เข้าทันทีและล้างตัวนับ เมื่อเซนเซอร์กลับมาปกติจะรับผลดิบในรอบนั้น

**ตัวอย่างสำคัญ:** เริ่มจาก WARNING แล้วค่ากลับเป็น NORMAL ดิบตลอด ผลที่ส่ง 6 รอบถัดไปคือ WARNING, WARNING, WATCH, WATCH, WATCH, NORMAL การลดครบสองระดับจึงใช้ 6 รอบ ไม่ใช่ลดจาก WARNING เป็น NORMAL หลัง 3 รอบ และจำนวนรอบนี้ไม่ใช่เวลาคงที่ เพราะคาบรายงานเปลี่ยนตามสถานะ

### 1.3 การอ่านค่าและแพ็กเก็ต

- Sharp อ่านด้วย `analogReadMilliVolts` จำนวน 3 ตัวอย่าง เลือกมัธยฐาน แล้วคำนวณ P = max(0, (V × G − V₀)/S) ค่าปัจจุบัน G = 1, V₀ = 600 mV, S = 5 mV/(µg/m³) ค่านี้เป็นการประมาณจากสมการในโค้ด ต้องตรวจการสอบเทียบและวงจรจริงก่อนกล่าวถึงความแม่นยำ
- SENSOR_FAULT หมายถึงความผิดปกติที่โปรแกรมตรวจพบ ไม่รับรองว่าจะตรวจพบการถอดสายหรือความเสียหายของ Sharp ได้ทุกแบบ การอ่านค่าแอนะล็อกที่ยังอยู่ในช่วงอาจไม่ถูกวินิจฉัยว่าเสีย
- แพ็กเก็ตข้อมูลวัด: `t, id, q, sid, ri, st, rb, rv, at, h, pm, sh` โดย `t="s"`, `rv=7` ไม่มี `c`, `sm`, Baseline หรือคะแนน
- `rb` เป็นบิตเหตุผล ไม่ใช่คะแนน: 1 อุณหภูมิระดับเตือนภัย; 2 อนุภาคระดับเตือนภัย; 4 ร้อนและแห้ง; 8 อุณหภูมิระดับเฝ้าระวัง; 16 อนุภาคระดับเฝ้าระวัง; 32 ความชื้นต่ำ; 64 เซนเซอร์ผิดปกติ; 128 กำลังคงสถานะก่อนลดระดับ
- พิกัดใช้แพ็กเก็ตแยก `t="gps"` ไม่ได้ใส่พิกัดในข้อมูลวัดทุกชุด

### 1.5 Gateway, Backend และ Dashboard

- LoRa ปัจจุบัน: 433 MHz, SF12, BW125 kHz, CR4/5, Sync Word 0x34, กำลังส่ง 20 dBm
- Gateway ส่ง ACK สำหรับข้อมูลวัดก่อนตรวจข้อมูลซ้ำและก่อนเพิ่มคิว HTTP คิวแพ็กเก็ตยาว 20 รายการอยู่ใน RAM หากคิวเต็มอาจทิ้งแพ็กเก็ตแม้ ACK ไปแล้ว การรีเซตทำให้คิวใน RAM สูญหายได้
- Backend ตรวจชนิดแพ็กเก็ต รหัสโหนด ลำดับ Session รุ่น 7 ความสอดคล้องของสถานะ/สุขภาพ/บิตเหตุผล และช่วงข้อมูลก่อนบันทึก; `riskFromPacket` คัดลอกสถานะกับเหตุผล ไม่คำนวณเกณฑ์ซ้ำ
- การตรวจซ้ำใช้ packet_id ที่ประกอบด้วย id, sid, q และชนิดแพ็กเก็ต และป้องกันข้อมูลลำดับเก่าใน Session เดียวกันไม่ให้ทับข้อมูลล่าสุด
- สร้างเหตุการณ์จาก WATCH, WARNING และ SENSOR_FAULT; NORMAL ปิดเหตุการณ์ที่ยังทำงาน เงื่อนไขคงสถานะก่อนกลับ NORMAL อยู่ที่โหนด ไม่ใช่รอ 3 รอบซ้ำอีกครั้งที่ Backend
- API `/api/packets` อาจตอบ 201 สำหรับแพ็กเก็ตซ้ำที่ตรวจพบด้วย ต้องดู `duplicate`/`ignored` และข้อมูลฐานข้อมูลประกอบ จึงจะยืนยันว่ามีการสร้าง reading ใหม่
- คำสั่งควบคุมปัจจุบันคือ `gps_reacquire`, `gps_manual` เท่านั้น การกำหนดพิกัดเองเก็บค่าที่ Backend และสั่งให้โหนดหยุดใช้ GPS อัตโนมัติ ไม่ควรอธิบายว่าค่าพิกัดที่กรอกถูกส่งไปเขียนใน GPS hardware
- Dashboard โหลดข้อมูลทุก 5 วินาทีผ่าน API; หน้าภาพรวมคัดโหนดออนไลน์ ส่วน Backend ยังส่งรายการโหนดออฟไลน์ให้ได้ สถานะ UNKNOWN/ออฟไลน์เป็นสถานะการแสดงผลหรือการเชื่อมต่อ ไม่ใช่ผลความเสี่ยงเพิ่มเติมของโหนด
- เกณฑ์ออฟไลน์ Backend ค่าเริ่มต้น max(60 วินาที, 2.5 × คาบรายงาน + 30 วินาที) เปลี่ยนได้ด้วย environment จึงห้ามเขียนว่า 60 วินาทีเสมอ
- โค้ดตรวจ Gateway Key และสิทธิ์ผู้ดูแลมีอยู่ แต่สถานะการตั้งค่า Cloudflare/บริการที่กำลังออนไลน์ต้องใช้หลักฐานการติดตั้งจริงประกอบ

### ที่มาของเกณฑ์: อ้างอิงได้ แต่ต้องบอกการดัดแปลง

ตรวจไฟล์ Computers หน้า 7 และ Designs หน้า 18 หัวข้อ 3.3 แล้ว:

บทคัดย่อ Designs ใช้หน่วยความเร็วลมไม่ตรงกับหัวข้อ 3.3 จึงควรระบุว่าทบทวนจากหัวข้อ 3.3 และไม่ยกหน่วยจากบทคัดย่อมาใช้โดยไม่ตรวจสอบ

ข้อความใต้รูปแนะนำ: **“ที่มา: ผู้จัดทำ โดยดัดแปลงแนวทางกำหนดเกณฑ์จาก [21], [32] และจัดลำดับการประเมินตามเฟิร์มแวร์ของโครงงาน”** ต้องตามด้วยย่อหน้าอธิบายว่า Sharp เป็นค่าประมาณ ไม่เท่ากับเครื่องวัด PM2.5 ของงานอ้างอิง และการคงสถานะ 3 รอบเป็นส่วนออกแบบของผู้จัดทำ

เลข [21]/[32] ตรวจจากไฟล์ `บรรณานุกรม_IEEE.docx` ที่อยู่ในโฟลเดอร์เดียวกัน ไม่พบรายการบรรณานุกรมท้ายไฟล์รวมที่ตรวจ จึงต้องตรวจการรวมเอกสารและเลขอ้างอิงอีกครั้ง ไฟล์บรรณานุกรมดังกล่าวยังมีหลายรายการเป็นรูปแบบผู้แต่ง–ปี แม้ชื่อไฟล์มี IEEE; สองรายการนี้เป็นรูปแบบ IEEE แล้ว แต่ยังเรียกทั้งบรรณานุกรมว่าเป็น IEEE สมบูรณ์ไม่ได้

**วิธีเพิ่ม latch ในรูป 3.6 โดยยังใช้สองรูปเดิม:** ให้กล่อง WARNING/WATCH/NORMAL เดิมหมายถึง “ผลประเมินเบื้องต้น” รวมลูกศรเข้าสู่กล่อง “ปรับสถานะตามผลประเมินและสถานะเดิม: ยกระดับทันที ลดระดับทีละขั้นหลังเข้าเงื่อนไขต่อเนื่อง 3 รอบ” แล้วจึงส่งไป A; ส่วน SENSOR_FAULT ไปกำหนดสถานะทันทีและล้างตัวนับก่อนรวมกับผลสุดท้าย เพิ่ม I→ตั้งค่าอุปกรณ์/โหลดข้อมูล GPS และ N→เริ่มรอบอ่านค่า ส่วนรายละเอียด latch แสดงในตารางหรือคำอธิบายประกอบได้

## 7. ข้อมูลที่ซอร์สยังตอบแทนหลักฐานจริงไม่ได้

1. บอร์ดแต่ละตัวแฟลชรุ่นใดอยู่ และ Backend/Dashboard ที่เปิดใช้งาน build เมื่อใด
2. แผงโซลาร์เซลล์5Wหรือ15W ความจุแบตเตอรี่ และการเดินสาย/รางจ่ายไฟที่ประกอบจริง
3. ผลสอบเทียบSharp ค่าแรงดันศูนย์/อัตราขยายของวงจรจริง และความเทียบเท่ากับPM2.5
4. วัน สถานที่ จำนวนรอบ ข้อมูลดิบและตัวนับของการทดสอบระยะLoRa รวมถึงเฟิร์มแวร์ที่ใช้ขณะนั้น
5. กระแสและระยะเวลาที่วัดจริง ผลทำงานต่อเนื่อง24ชั่วโมง ความแม่นยำ และอัตราแจ้งผิดของรุ่น7
6. การเปิดใช้Telegram/Cloudflareจริงและผลทดสอบคำสั่งจากDashboardถึงโหนด

รายการเหล่านี้ต้องแนบหลักฐานหรือระบุ “ยังไม่ทดสอบ/ยังไม่ยืนยัน” ไม่เลือกตัวเลขหรือเติมผลให้เอง
