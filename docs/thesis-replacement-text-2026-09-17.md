# ข้อเสนอข้อความทดแทนบทที่ 1–3 ตามซอร์สรุ่น 7

ใช้ร่วมกับ [รายงานตรวจความสอดคล้อง](thesis-audit-2026-09-17.md) วันที่ 17 กันยายน 2569 ข้อความต่อไปนี้อธิบายสิ่งที่ซอร์สปัจจุบันออกแบบให้ทำ ไม่ใช่ผลทดลองฮาร์ดแวร์ที่ตรวจยืนยันแล้ว ไม่ควรนำไปแทนข้อความผลทดลองในบทที่ 4 โดยอัตโนมัติ

เลขอ้างอิง [21] และ [32] ยึดรายการใน `บรรณานุกรม_IEEE.docx` ที่ตรวจครั้งนี้ ต้องตรวจลำดับอีกครั้งเมื่อรวมเล่มและจัดรูปแบบตามคู่มือสถาบัน

## บทที่ 1

### แทนย่อหน้าอธิบายวิธีประเมินในความเป็นมา P0006–0007

การประเมินสถานะของระบบดำเนินการภายใน Sensor Node โดยตรวจสอบความถูกต้องของข้อมูลจากเซนเซอร์ก่อนนำค่าอุณหภูมิ ความชื้นสัมพัทธ์ และความเข้มข้นอนุภาคโดยประมาณมาเปรียบเทียบกับเกณฑ์ที่กำหนด ผลการประเมินประกอบด้วย NORMAL, WATCH, WARNING และ SENSOR_FAULT โดยระบบยกระดับความเสี่ยงทันทีเมื่อเข้าเงื่อนไข และใช้การตรวจพบค่าที่ต่ำกว่าระดับเดิมต่อเนื่องสามรอบก่อนลดระดับทีละขั้น จากนั้นโหนดส่งค่าตรวจวัด สถานะ และเหตุผลประกอบการประเมินผ่าน LoRa ไปยัง Gateway เพื่อส่งต่อไปยัง Backend ซึ่งตรวจสอบรูปแบบและข้อมูลซ้ำ จัดเก็บข้อมูลใน MongoDB และจัดการเหตุการณ์แจ้งเตือนตามสถานะที่โหนดรายงาน เว็บ Dashboard แสดงข้อมูลปัจจุบัน ตำแหน่ง ประวัติเหตุการณ์ และกราฟแนวโน้มผ่าน API ของ Backend

### วัตถุประสงค์ข้อที่ 3 แทน P0012

เพื่อพัฒนาวิธีประเมินสถานะจากอุณหภูมิ ความชื้นสัมพัทธ์ และความเข้มข้นอนุภาคโดยประมาณภายใน Sensor Node โดยใช้เกณฑ์ที่กำหนดร่วมกับกลไกคงสถานะก่อนลดระดับ และตรวจสอบความถูกต้องของแพ็กเก็ตที่ระบบส่วนกลาง

### สมมติฐาน แทน P0016

เมื่อ Sensor Node ได้รับค่าตรวจวัดที่ผ่านการตรวจสอบความถูกต้อง ระบบจะสามารถจำแนกสถานะและเปลี่ยนสถานะได้สอดคล้องกับเกณฑ์ที่กำหนด รวมทั้งส่งค่าตรวจวัด สถานะ และเหตุผลผ่าน LoRa และ Gateway ไปจัดเก็บและแสดงผลในระบบส่วนกลางได้ โดยการประเมินสมมติฐานจะตรวจเปรียบเทียบผลที่คาดหวังกับผลที่เกิดขึ้นจริงในแต่ละกรณีทดสอบ ทั้งนี้ ความสามารถในการตรวจพบไฟป่าและอัตราการแจ้งเตือนผิดพลาดต้องได้รับการประเมินจากข้อมูลทดลองเพิ่มเติม

### ข้อตกลงเรื่องการวัด แทน P0022

การแปลงแรงดันจาก Sharp เป็นความเข้มข้นอนุภาคใช้ค่าคงที่ที่กำหนดในเฟิร์มแวร์ ผลลัพธ์จึงเป็นค่าประมาณซึ่งต้องตรวจสอบกับวงจรและเครื่องมืออ้างอิงก่อนใช้สรุปความแม่นยำหรือเทียบเท่าค่า PM2.5 ส่วนเกณฑ์ประเมินเป็นเกณฑ์สำหรับต้นแบบที่ต้องทดสอบความเหมาะสมภายใต้สภาพแวดล้อมที่ใช้งาน

### ขอบเขตด้านการสื่อสารและซอฟต์แวร์

ระบบใช้ Sensor Node หลักสองชุด ได้แก่ NODE01 และ NODE02 ส่งข้อมูลไปยัง Gateway ผ่าน LoRa ความถี่ 433 MHz โดยซอร์สปัจจุบันกำหนด Spreading Factor เท่ากับ 12, Bandwidth เท่ากับ 125 kHz, Coding Rate เท่ากับ 4/5, Sync Word เท่ากับ 0x34 และกำลังส่ง 20 dBm Gateway ส่งข้อมูลต่อผ่าน Wi-Fi ด้วย HTTP ไปยัง Backend ขณะที่ Serial Monitor ใช้ติดตามและตรวจสอบการทำงานของอุปกรณ์ สำหรับ NODE03 เป็นชุดส่งข้อมูลจำลองที่ใช้ทดสอบระยะการสื่อสารแยกจากโหนดตรวจวัดหลัก

ระบบส่วนกลางจัดเก็บค่าตรวจวัด สถานะ เหตุผล และข้อมูลคุณภาพสัญญาณ รองรับเหตุการณ์ WATCH, WARNING และ SENSOR_FAULT รวมทั้งปิดเหตุการณ์เมื่อได้รับสถานะ NORMAL ฟังก์ชันควบคุมจากผู้ดูแลประกอบด้วยการร้องขอให้ค้นหาพิกัด GPS ใหม่และการกำหนดพิกัดด้วยตนเอง ส่วนหน้า Dashboard แสดงผลผ่าน API และเรียกข้อมูลใหม่ทุกห้าวินาที ระยะเวลาดังกล่าวเป็นรอบปรับปรุงหน้าเว็บ ไม่ใช่การรับประกันเวลาหน่วงรวมตั้งแต่ตรวจวัดจนถึงแสดงผล

### ตัวแปรตาม แทน P0060

ตัวแปรตาม ได้แก่ ค่าตรวจวัดจากเซนเซอร์ สถานะและเหตุผลการประเมิน ลำดับการเปลี่ยนสถานะ จำนวนรอบที่ได้รับ ACK จำนวนครั้งที่ส่งซ้ำ เวลาหน่วงในการส่งข้อมูล ค่า RSSI และ SNR ตลอดจนความสอดคล้องระหว่างข้อมูลต้นทาง ข้อมูลในฐานข้อมูล และข้อมูลที่แสดงบน Dashboard

หากไม่ได้เก็บตัวแปรบางรายการจริง ให้ลดขอบเขตให้ตรงกับแผนทดสอบ ไม่เติมผลย้อนหลัง

### ประโยชน์ที่คาดว่าจะได้รับ แทน P0067

ได้แนวทางประเมินสถานะที่สามารถตรวจย้อนกลับจากค่าตรวจวัดและเหตุผลประกอบ รวมทั้งกลไกคงสถานะก่อนลดระดับเพื่อลดการสลับสถานะระหว่างช่วงที่ค่าตรวจวัดกำลังกลับสู่สภาวะปกติ

### คำนิยามที่ควรใช้แทน P0075–0077

- **เกณฑ์ประเมินสถานะ** หมายถึง เงื่อนไขเปรียบเทียบค่าอุณหภูมิ ความชื้นสัมพัทธ์ และอนุภาคโดยประมาณที่กำหนดในเฟิร์มแวร์ เพื่อจัดสถานะเบื้องต้น
- **การคงสถานะก่อนลดระดับ** หมายถึง การเก็บสถานะเดิมไว้จนตรวจพบเงื่อนไขลดระดับต่อเนื่องสามรอบ โดยลดจาก WARNING เป็น WATCH และจาก WATCH เป็น NORMAL ทีละขั้น
- **สถานะจาก Sensor Node** หมายถึง NORMAL, WATCH, WARNING หรือ SENSOR_FAULT โดย SENSOR_FAULT ระบุปัญหาของการตรวจวัด ไม่ใช่ระดับความรุนแรงของไฟที่สูงกว่า WARNING
- **ความเข้มข้นอนุภาคโดยประมาณ** หมายถึง ค่าที่แปลงจากแรงดันของ Sharp GP2Y1014AU0F ตามสมการและค่าคงที่ในเฟิร์มแวร์ มีหน่วย µg/m³ และยังไม่ถือเป็นค่า PM2.5 ที่ผ่านการสอบเทียบ

## บทที่ 2

### แนวทางที่ใช้ในการประเมินสถานะของโครงงาน

ระบบใช้การประเมินแบบกฎ โดยกำหนดเงื่อนไขที่สามารถตรวจสอบได้จากค่าตรวจวัดปัจจุบัน ก่อนประเมินสถานะจะตรวจสอบความสมเหตุสมผลของข้อมูลอุณหภูมิและความชื้น รวมทั้งผลการอ่านค่าจาก Sharp หากตรวจพบความผิดปกติ ระบบกำหนดสถานะ SENSOR_FAULT ส่วนข้อมูลที่ผ่านการตรวจสอบจะถูกประเมินตามลำดับ WARNING, WATCH และ NORMAL การเรียงลำดับนี้ทำให้เงื่อนไขระดับเตือนภัยมีความสำคัญก่อนระดับเฝ้าระวัง

ในการอ่าน Sharp เฟิร์มแวร์อ่านแรงดันสามตัวอย่างและเลือกมัธยฐาน เพื่อลดผลของค่ากระโดดบางตัวอย่าง จากนั้นแปลงแรงดันเป็นความเข้มข้นอนุภาคโดยประมาณตามสมการ

**P = max(0, (V × G − V₀) / S)**

โดย V เป็นแรงดันที่อ่านได้ในหน่วยมิลลิโวลต์ G เป็นตัวคูณชดเชยวงจร V₀ เป็นแรงดันอ้างอิงเมื่อไม่มีอนุภาคตามค่าที่ตั้งไว้ และ S เป็นความไวในการแปลงแรงดันเป็นค่าประมาณอนุภาค ซอร์สปัจจุบันตั้ง G = 1, V₀ = 600 mV และ S = 5 mV/(µg/m³) การใช้ค่าคงที่ดังกล่าวไม่ได้ทดแทนการสอบเทียบอุปกรณ์แต่ละชุดกับเครื่องมืออ้างอิง

หลังได้สถานะเบื้องต้น ระบบใช้สถานะจากรอบก่อนเพื่อควบคุมการลดระดับ โดยยกระดับทันทีเมื่อเงื่อนไขสูงขึ้น แต่ลดระดับเมื่อพบผลที่ต่ำกว่าระดับเดิมต่อเนื่องสามรอบ กรณี WARNING จะลดเป็น WATCH ก่อน แม้ค่าตรวจวัดจะกลับอยู่ในเกณฑ์ NORMAL แล้ว จากนั้นต้องพบผล NORMAL ต่อเนื่องอีกสามรอบจึงลดเป็น NORMAL กลไกนี้ใช้ควบคุมการกลับสู่สภาวะปกติ ไม่ได้เป็นการรอยืนยันหลายรอบก่อนแจ้ง WARNING

### ที่มาของเกณฑ์จากงานวิจัย

Makdee และคณะ [21] เสนอระบบเตือนภัยไฟป่าที่ใช้ LoRa และจัดประเภทข้อมูลโดยพิจารณาอุณหภูมิ ค่าควัน และ PM2.5 โดยในหน้าที่ 7 กำหนดเกณฑ์อุณหภูมิและ PM2.5 สำหรับระดับ Fire ที่สูงกว่า 45°C และ 150 µg/m³ ตามลำดับ และมีระดับ Surveillance สำหรับช่วงค่าที่ต่ำกว่าเกณฑ์ดังกล่าว โครงงานนี้ใช้ตัวเลขอุณหภูมิ 35°C และ 45°C รวมทั้งค่าอนุภาค 50 และ 150 µg/m³ เป็นแนวทางในการกำหนดเกณฑ์ อย่างไรก็ตาม อุปกรณ์ Sharp ของโครงงานให้ค่าประมาณอนุภาคซึ่งแตกต่างจากการวัด PM2.5 ในบทความ จึงเป็นการดัดแปลงแนวทางและยังต้องทดสอบความเหมาะสมของเกณฑ์กับอุปกรณ์จริง

Pires และคณะ [32] อธิบายในหัวข้อ 3.3 ว่าพิจารณาอย่างน้อยสองในสามเงื่อนไข ได้แก่ อุณหภูมิอย่างน้อย 30°C ความชื้นสัมพัทธ์ไม่เกิน 30% และความเร็วลมอย่างน้อย 30 km/h โครงงานนี้ไม่มีเซนเซอร์ความเร็วลม จึงเลือกใช้เฉพาะเงื่อนไขอุณหภูมิอย่างน้อย 30°C ร่วมกับความชื้นสัมพัทธ์ไม่เกิน 30% เป็นเหตุผลหนึ่งของสถานะ WARNING การเลือกดังกล่าวไม่ครอบคลุมทุกคู่เงื่อนไขของงานต้นฉบับ

ส่วนการกำหนด WATCH เมื่อความชื้นต่ำกว่า 50% การให้ SENSOR_FAULT มีลำดับประเมินก่อน และการคงสถานะก่อนลดระดับต่อเนื่องสามรอบ เป็นกฎที่กำหนดในโครงงานโดยอาศัยบริบทของระบบ จึงต้องอธิบายแยกจากเงื่อนไขที่นำมาจากงานวิจัยและตรวจสอบด้วยการทดลองของโครงงาน

### บทบาทซอฟต์แวร์ส่วนกลาง

Gateway ทำหน้าที่รับแพ็กเก็ต LoRa ส่งข้อความตอบรับสำหรับข้อมูลวัด และนำข้อมูลเข้าคิวเพื่อส่งต่อไปยัง Backend ผ่าน Wi-Fi/HTTP การส่ง ACK เป็นการยืนยันการรับที่ Gateway ส่วนความสำเร็จในการบันทึกข้อมูลต้องตรวจที่ Backend และฐานข้อมูลเพิ่มเติม Backend ตรวจสอบความถูกต้องของแพ็กเก็ต ป้องกันข้อมูลซ้ำ และแปลงบิตเหตุผลให้อยู่ในรูปแบบที่จัดเก็บและแสดงผลได้ โดยใช้สถานะที่ Sensor Node ส่งมาเป็นผลประเมินหลัก

Dashboard พัฒนาด้วย React และ TypeScript และรับข้อมูลผ่าน API ของ Backend ส่วน MongoDB ติดต่อผ่าน Backend หน้าเว็บเรียกข้อมูลใหม่ทุกห้าวินาทีและใช้ข้อมูลของโหนดที่ออนไลน์สำหรับภาพรวมปัจจุบัน ระบบมีการแสดงสถานะการเชื่อมต่อแยกจากสถานะความเสี่ยง เพื่อไม่ให้การขาดข้อมูลถูกตีความว่าเป็นสภาวะปกติ

## บทที่ 3

### ข้อความแทนส่วนการทำงานของ Sensor Node P0348–0354

เมื่อเริ่มต้นระบบหรือกลับจาก Deep Sleep โปรแกรมดำเนินการตั้งค่าอุปกรณ์ เซนเซอร์ วิทยุ LoRa และข้อมูลที่เกี่ยวข้องกับการระบุตำแหน่ง จากนั้นเริ่มรอบการตรวจวัดโดยบันทึกเวลาเริ่มรอบ อ่านค่าอุณหภูมิและความชื้นจาก SHT31 และอ่านแรงดันจาก Sharp สามตัวอย่างเพื่อเลือกค่ามัธยฐานก่อนแปลงเป็นความเข้มข้นอนุภาคโดยประมาณ

ระบบตรวจสอบความถูกต้องของข้อมูลก่อนประเมิน หากตรวจพบความผิดปกติตามเงื่อนไขที่กำหนดจะรายงาน SENSOR_FAULT สำหรับข้อมูลที่ผ่านการตรวจสอบ ระบบเปรียบเทียบเกณฑ์ WARNING ก่อน WATCH และกำหนด NORMAL เมื่อไม่เข้าเงื่อนไขทั้งสองระดับ จากนั้นใช้กลไกคงสถานะซึ่งยกระดับทันทีและลดระดับทีละขั้นเมื่อเข้าเงื่อนไขลดระดับต่อเนื่องสามรอบ สถานะและเหตุผลหลังผ่านกลไกดังกล่าวจะถูกใช้สร้างแพ็กเก็ตและกำหนดคาบรายงาน

โหนดสร้างแพ็กเก็ต JSON ข้อมูลวัดหนึ่งชุดต่อรอบ โดยกำหนดลำดับแพ็กเก็ตใหม่สำหรับข้อมูลชุดใหม่ หากต้องส่งซ้ำจะใช้ข้อมูลและลำดับเดิม แต่ละความพยายามส่งมีการสุ่มหน่วงเวลา 0–5 วินาที เมื่อส่งออกได้ โหนดเปิดรับ ACK และคำสั่งเป็นเวลาหกวินาที โดยยอมรับ ACK ของข้อมูลวัดเมื่อชนิดข้อความและค่า id, sid และ q ตรงกับข้อมูลที่รอการยืนยัน หากยังไม่ได้รับ ACK จะส่งซ้ำได้รวมสูงสุดสามครั้ง เมื่อครบจำนวนที่กำหนดจะจบการส่งชุดนั้นและดำเนินงานต่อ

หลังขั้นตอนส่งข้อมูล โปรแกรมประมวลผลงาน GPS และส่งรายงานพิกัดที่รออยู่ในแพ็กเก็ตแยก ในสถานะ WARNING โหนดคงการทำงานและรอเวลาที่เหลือให้ครบคาบเป้าหมายยี่สิบวินาที ในสถานะอื่น หากยังมีงานค้นหาหรือรายงาน GPS จะปิดไฟเลี้ยงราง Sharp ที่ควบคุมและดำเนินงาน GPS จนเสร็จหรือถึงรอบวัดถัดไป หากงานเสร็จก่อนครบคาบจะเข้าสู่ Deep Sleep ตามเวลาที่เหลือ โดยกำหนดคาบเป้าหมาย NORMAL และ SENSOR_FAULT เท่ากับห้านาที และ WATCH เท่ากับสองนาที เมื่อครบเวลาปลุก โปรแกรมเริ่ม setup ใหม่ ส่วนกรณีที่ไม่เข้าสู่ Deep Sleep จะเริ่มรอบตรวจวัดถัดไปผ่าน loop

### คำอธิบายรูป 3.6 หลังเพิ่มกลไกคงสถานะในรูปแล้ว

จากรูปที่ 3.6 Sensor Node ตรวจสอบความถูกต้องของข้อมูลจาก SHT31 และ Sharp ก่อนเปรียบเทียบเกณฑ์ โดยตรวจ WARNING ก่อน WATCH และกำหนด NORMAL เมื่อไม่เข้าเงื่อนไขระดับที่สูงกว่า ผลเบื้องต้นถูกนำไปปรับร่วมกับสถานะเดิม โดยยกระดับทันทีและลดระดับทีละขั้นเมื่อพบเงื่อนไขลดระดับต่อเนื่องสามรอบ ส่วนความผิดปกติของเซนเซอร์รายงานเป็น SENSOR_FAULT จากนั้นส่งสถานะและเหตุผลสุดท้ายไปยังจุดเชื่อม A เพื่อสร้างและส่งแพ็กเก็ตตามรูปที่ 3.7

ที่มา: ผู้จัดทำ โดยดัดแปลงแนวทางกำหนดเกณฑ์จาก [21], [32] และจัดลำดับการประเมินตามเฟิร์มแวร์ของโครงงาน

ต้องแนบคำอธิบายความแตกต่างระหว่างค่าประมาณ Sharp กับ PM2.5 และส่วนที่ผู้จัดทำออกแบบเองตามบท2ด้วย การอ้างอิงใต้รูปเพียงบรรทัดเดียวไม่แสดงที่มาของทุกเงื่อนไขได้ครบ

### คำอธิบายรูป 3.7 หลังแก้ข้อความในกล่อง

จากรูปที่ 3.7 โหนดสร้างข้อมูลวัดหนึ่งชุดและส่งผ่าน LoRa โดยสุ่มหน่วงก่อนส่งแต่ละครั้ง เมื่อส่งออกได้จะเปิดรับ ACK และคำสั่งจาก Gateway เป็นเวลาหกวินาที หากไม่ได้รับ ACK ที่ตรงกับรหัสโหนด Session และลำดับแพ็กเก็ต จะส่งข้อมูลชุดเดิมซ้ำรวมไม่เกินสามครั้ง จากนั้นประมวลผลงาน GPS และกำหนดการทำงานตามสถานะ โดย WARNING คงการทำงานเพื่อเริ่มรอบใหม่ตามคาบเป้าหมายยี่สิบวินาที ส่วนสถานะอื่นเข้าสู่ Deep Sleep ตามเวลาที่เหลือเมื่อไม่มีงาน GPS ค้าง จุดเชื่อม N หมายถึงการกลับเข้าสู่ขั้นตอนอ่านค่าในรอบถัดไปโดยไม่เริ่ม setup ใหม่ และจุดเชื่อม I หมายถึงการเริ่มต้นอุปกรณ์หลังตื่นจาก Deep Sleep ทั้งนี้ ACK ยืนยันการรับแพ็กเก็ตที่ Gateway ผ่าน LoRa ส่วนการบันทึกข้อมูลในฐานข้อมูลต้องตรวจสอบแยกต่างหาก

### ข้อความแทนส่วน Backend P0371–0378

Backend พัฒนาด้วย Node.js และ Express และเชื่อมต่อ MongoDB ผ่าน Mongoose เมื่อได้รับคำขอจาก Gateway จะตรวจสอบกุญแจในส่วนหัว X-Gateway-Key ก่อนตรวจชนิดและโครงสร้างแพ็กเก็ต สำหรับข้อมูลวัด ระบบตรวจรหัสโหนด Session ลำดับแพ็กเก็ต รุ่นกฎ สถานะ สุขภาพเซนเซอร์ บิตเหตุผล และช่วงของค่าตรวจวัด จากนั้นตรวจแพ็กเก็ตซ้ำและข้อมูลลำดับเก่าใน Session เดียวกัน

แพ็กเก็ตที่ผ่านการตรวจสอบจะถูกแปลงเป็นโครงสร้างข้อมูลสำหรับจัดเก็บ โดยคงสถานะที่ Sensor Node ประเมินมาและถอดความหมายของบิตเหตุผลเป็นรายการเหตุผล Backend บันทึกข้อมูลลงใน readings และปรับปรุงข้อมูลล่าสุดใน nodes โดยไม่คำนวณเกณฑ์หรือคะแนนความเสี่ยงซ้ำ จากนั้นจัดการเหตุการณ์ใน alerts เมื่อพบ WATCH, WARNING หรือ SENSOR_FAULT และปิดเหตุการณ์ที่ยังทำงานเมื่อได้รับ NORMAL การส่งข้อความ Telegram ขึ้นอยู่กับการตั้งค่าบริการและผลการส่งจริง

### ส่วน Dashboard และคำสั่งผู้ดูแล

Dashboard รับข้อมูลสถานะ ค่าตรวจวัด พิกัด เหตุการณ์ และข้อมูลย้อนหลังผ่าน REST API โดยกำหนดรอบเรียกข้อมูลทุกห้าวินาที หน้าภาพรวมใช้ข้อมูลของโหนดที่ยังออนไลน์ประกอบการแสดงสถานการณ์ และแสดงว่าไม่สามารถประเมินสถานการณ์ปัจจุบันได้เมื่อองค์ประกอบที่จำเป็นขาดการเชื่อมต่อ กราฟย้อนหลังเลือกช่วงหนึ่งชั่วโมง แปดชั่วโมง หนึ่งวัน หนึ่งสัปดาห์ หนึ่งเดือน หรือหนึ่งปีได้ตามตัวเลือกของระบบ

ผู้ดูแลสามารถร้องขอให้ Sensor Node ค้นหาพิกัดใหม่ผ่าน `POST /api/nodes/:node_id/gps/reacquire` หรือกำหนดพิกัดด้วยตนเองผ่าน `POST /api/nodes/:node_id/location/manual` โดย Backend ตรวจสิทธิ์และจัดคิวคำสั่ง GPS ให้ Gateway ส่งต่อในช่วงที่โหนดเปิดรับคำสั่ง การได้รับการตอบรับคำสั่งกับการได้พิกัดใหม่เป็นคนละขั้นตอนและควรตรวจผลแยกกัน

### แก้คำอธิบายการทดสอบ NODE03

NODE03 ใช้เฟิร์มแวร์ทดสอบระยะโดยส่งแพ็กเก็ตข้อมูลจำลองหนึ่งชุดต่อรอบ กำหนดจำนวนความพยายามส่งสูงสุดสามครั้ง และสุ่มหน่วง0–5วินาทีก่อนส่งแต่ละครั้ง เมื่อส่งออกได้จะรอACKไม่เกินหกวินาที หลังจบรอบโปรแกรมพักห้าวินาทีก่อนเริ่มรอบถัดไป แม้แพ็กเก็ตระบุคาบรายงาน10วินาที แต่เวลาระหว่างการเริ่มรอบจริงขึ้นกับการสุ่มหน่วง เวลาส่ง เวลารอACK และจำนวนครั้งที่ส่งซ้ำ จึงต้องวัดจากเวลาจริงในการทดลอง

**อัตราสำเร็จของรอบที่ได้รับACK (%) = จำนวนรอบที่ได้รับACKที่ถูกต้อง ÷ จำนวนรอบที่ดำเนินการทั้งหมด × 100**

ต้องกำหนดชุดนับสำหรับแต่ละระยะและบันทึกจำนวนจริง เช่น สำเร็จกี่รอบจากทั้งหมดกี่รอบ ตัวนับสะสมจากการเปิดเครื่องต้องไม่ถูกนำมาอ้างว่าเป็นอัตราเฉพาะระยะล่าสุดโดยไม่หักตัวนับเริ่มต้น ค่าRSSI/SNRต้องระบุว่าวัดที่Gatewayขณะรับuplink หรือที่NODE03ขณะรับACK เพราะเป็นคนละทิศทาง

### การทดสอบพลังงาน

ควรวัดกระแสและเวลาเป็นกรณีแยก ได้แก่ GPSไม่ทำงานและได้รับACKครั้งแรก GPSไม่ทำงานและส่งครบสามครั้ง GPSกำลังค้นพิกัด และสถานะWARNINGที่ไม่เข้าสู่Deep Sleep จุดวัดต้องคงที่และระบุว่าอยู่ด้านแบตเตอรี่หรือด้าน5Vของวงจรเพิ่มแรงดัน การคำนวณกระแสเฉลี่ยต้องใช้ช่วงเวลาที่ไม่ซ้อนกันภายในกรณีเดียวกันตามสมการ Iเฉลี่ย = Σ(Iᵢtᵢ)/Σtᵢ โดยไม่รวมกรณีได้รับACKครั้งแรกกับกรณีส่งครบสามครั้งเป็นรอบเดียว และไม่ถือว่าค่ากระแสต่ำสุดของชิปเท่ากับกระแสของอุปกรณ์ทั้งชุด

## สิ่งที่ต้องเก็บหลักฐานก่อนกรอกผล

- วันเวลา สถานที่ NODE_ID รุ่นกฎ/รุ่นเฟิร์มแวร์ TEST_MODE และค่าพารามิเตอร์ขณะทดลอง
- ค่าT/RH/Pและแรงดันที่เกี่ยวข้อง สถานะก่อนหน้า ผลดิบ ผลหลังคงสถานะ และเหตุผล
- id/sid/q จำนวนattempts ผลACK ผลHTTP และreadingที่จับคู่กันได้
- จำนวนรอบสำเร็จ/ทั้งหมดแยกตามระยะ; ทิศทางRSSI/SNRและวิธีวัดระยะ
- จุดวัดกระแส ย่านและหน่วยของเครื่องมือ เวลาในแต่ละขั้น และข้อมูลทำงานต่อเนื่อง
- ภาพหน้าเว็บ/ฐานข้อมูลที่แสดงข้อมูลรุ่น7 พร้อมปิดบังข้อมูลกุญแจหรือข้อมูลลับก่อนใส่เล่ม

ข้อมูลเหล่านี้เป็นรายการที่ต้องเก็บ ไม่ใช่การยืนยันว่าผู้จัดทำได้ทดสอบครบแล้ว
